当前安装已包含 `docvortex/_native.abi3.so`，协议 35。未设置计算后端时，`auto` 实际选中 Rust，无加载失败。无需安装或重新编译扩展。
扩展 SHA256：`111b307c52688017f5a9f380cbded6e18eaf00b11be9a1b1a4375dd330032bae`。
用标准 Python c_call 事件单独验证真实图像接口：auto 和显式 rust 均调用 `image_contours`、`image_resize` 原生函数；显式 python 均不调用。三种模式的轮廓与缩放结果校验值完全一致。
前次整本计时未记录 backend_info；不能把新进程检查冒充旧进程的直接运行时记录。同一安装的当前 auto 行为与显式 rust 复测均证明不存在缺失 Rust 扩展的问题。

## OCR det 为何较慢

生产采样共 84 次 det 调用，82 种形状，其中 batch=1 有 32 次。真实方向检测输入为 `[1,3,960,320]`。
生产累计推理 CPU 2.514 秒，GPU 3.090 秒，差 0.577 秒；约占此前 GPU 整本平均耗时的 0.61%。这不是整本耗时较长的主要来源。
在独立新进程中，按生产全部 84 次输入形状和顺序回放。像素由同一个真实捕获张量重复构造，属于形状诊断，不能冒充 84 批原始图片的逐内容回放。卷积检测图没有按图像内容改变控制流。
第一遍包含该会话各形状的首次使用；随后完整回放五遍，报告五遍总时长中位数。不清理驱动磁盘缓存，因此首遍不能称为冷驱动或冷着色器缓存。所有计时包含同步返回 CPU，概率图仍供 DB 后处理使用。

| 路线 | 第一遍 84 次（秒） | 预热后 84 次中位数（秒） |
|---|---:|---:|
| CPU | 1.778 | 1.816 |
| 当前 NHWC WebGPU | 3.430 | 2.784 |
| GPU 输出绑定＋完整回读 | 3.022 | 2.886 |
| 预分配 GPU 输出＋完整回读 | 3.091 | 2.895 |
| NCHW WebGPU | 3.512 | 2.873 |

| 输入 | CPU（ms） | 当前 WebGPU（ms） |
|---|---:|---:|
| actual_orientation `[1, 3, 960, 320]` | 16.552 | 20.776 |
| derived_small `[1, 3, 128, 160]` | 1.327 | 4.454 |
| derived_large_batch `[16, 3, 192, 704]` | 121.737 | 121.939 |

真实输入的独立 ORT profile：158 个 WebGPU 节点、0 个 CPU 节点。没有发现图内算子回退导致的拖慢。
小输入 GPU 明显慢，大批输入接近持平；预热后整组仍慢。因此动态形状首次使用是附加开销，但不是唯一原因。证据更指向小模型下 GPU 提交、传输、同步等固定成本难以摊薄，以及当前 GPU 内核对该模型缺少吞吐优势。当前 host-side ORT profile 不能精确拆出各项 GPU 时间。
输出绑定、预分配输出、NCHW 均未改善整组耗时，因此不接入生产。[ORT I/O Binding 文档](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html)说明普通 Run 包含设备拷贝；本次所有绑定实验也完整计入 CPU 回读，避免比较异步排队与同步完成。
更实际的方向是让 det 单独选 CPU，其余模型继续 GPU；按本次生产采样只能省约 0.6 秒，收益较小。减少尺寸种类、合并批次也有实验空间，但会增加填充和计算，必须验证完整检测结果。
Graph Capture 要求静态形状且全部计算在 WebGPU；当前动态检测路径不能直接打开该开关，需先改固定形状/分桶并另做正确性验证。[ORT WebGPU 文档](https://onnxruntime.ai/docs/execution-providers/WebGPU-ExecutionProvider.html)

真实方向检测张量 CPU/GPU 的 0.3 二值掩码完全一致；大批量衍生输入有 1 个阈值像素不同。绑定实验与各自常规 GPU 调用结果一致，已检查改变输入时不会读到旧结果。数值差异与最终完整结果一致性分别记录，未宣称浮点输出逐值相等。

## 正式环境的校准次数

`model.onnx_device=auto` 首次实际加载适用模型时启动 1 个新校准子进程。六图按宽高比预处理成一个 `[6,3,48,1012]` batch，CPU 先测、GPU 后测。
每个后端总共 3 次 batch 推理：第 1 次预热不计，后 2 次耗时求和。GPU 两次之和 / CPU 两次之和 ≤ 0.8 则选 GPU。另检查重复解码稳定、CPU/GPU 解码一致及实际 EP，子进程超时 15 秒。
正常配置文件的 auto 成功后保存 cpu/gpu，后续进程直接复用该配置，不重新校准。同进程也缓存结果。若用环境变量指定 auto，则只缓存于当前进程，不保存文件；新进程会重新校准。显式 cpu/gpu 跳过性能校准。此前的 5 次是验证脚本的独立重复次数。

## 是否提高 0.8 阈值

补测 10 次正式协议，CPU-first、每次新进程：0.423690, 0.803812, 0.688023, 0.466114, 0.872854, 0.724064, 0.432303, 0.541350, 0.729099, 0.717773。
范围 0.424–0.873，中位数 0.703；8 次选 GPU、2 次选 CPU。整本 GPU 确实更快，说明当前单次短校准存在误判风险。

| 比值阈值 | 这 10 次中选 GPU |
|---|---:|
| 0.8 | 8/10 |
| 0.85 | 9/10 |
| 0.9 | 10/10 |

诊断协议改为每端预热 3 次、计时 7 次取中位数，5 次比值：0.697680, 0.433023, 0.750388, 0.622433, 0.496510，全部选 GPU；但数值仍有明显变化，不能宣称已解决稳定性。
正式协议的 CPU 单次计时约 120–215 ms，GPU 多数约 86–110 ms。不同进程的 CPU 速度变化明显；这台机器有不同最高频率的核，系统调度、频率和桌面负载可能影响短采样，当前数据不能将原因唯一归为其中一项。
附加诊断将工作进程限制在 CPU 0–3（4.9 GHz 的四个核），5 次比值：0.798250, 1.242293, 0.706290, 0.740167, 0.741198。CPU 单次收窄到约 119–134 ms，但 GPU 仍有一次延迟突增；该次即使阈值 0.9 也会选 CPU。亲和性仅在诊断子进程生效，生产设置未变。
因此建议先改善采样稳定性：增加预热/采样、使用中位数，接近阈值时新进程复测，并记录运行环境。更长采样已在本机验证方向，但落入生产还需超时与跨机回归。
0.8 是要求 rec 至少节省 20% 的策略门槛，不是硬件兼容线。提高到 0.85/0.9 会放宽 GPU 选择，不能消除噪声，且 rec 仅为整条流水线的代理指标。当前只有正收益机器的数据，不据此修改 WebGPU 全局阈值，DML 阈值也保持不变。
这台主机的整本结果已经验证 GPU 更快，可显式选 gpu，避开重复短采样。若目标是调整全局阈值，需要补充 CPU 胜出的 Linux 机器，或采用更能代表 layout/MFR/rec 的组合校准。
