# i7-12700：校准轮次与 NHWC 禁用预打包完整验证

> 历史归档：保留原设计或验收时的记录，不作为当前版本的安装、接口或实现指引。
> 当前入口见 [开发文档](https://opendatalab.github.io/MinerU/next/)；当时的版本、测试结论和未完成事项不追溯改写。

2026-10-21；i7-12700 / UHD 770 / RTX 3060 Ti；接续[三设备完整测试](onnx-i7-12700-webgpu-validation.md)和[3＋7 中位数校准诊断](onnx-i7-12700-calibration-median-diagnosis.md)。

**NHWC＋禁用 prepacking 未能让 UHD 770 稳定、正确地完成完整流程：第一遍完成但有明显内容错误，第二遍发生 GPU HANG。**
3060 Ti 的相同开关两次均得到与 CPU 完全一致的结果，平均耗时增加约 1.19%。

## 校准一次需要多久，能否减少轮次

下表是完整 `resolve_onnx_device()` 的墙钟时间中位数，包含设备发现、模型校验、启动校准 worker、创建 CPU/GPU 会话和推理校验。
不包含调用方的 Python 模块导入、模型下载或首次派生图生成。每个数字来自 5 个独立新进程；每个协议共 10 次。
两列分别使用已有 shader 缓存和每个进程独立的新 `MESA_SHADER_CACHE_DIR`；后者并不代表操作系统、模型文件等所有缓存均冷。

| 预热＋计时，取中位数 | 已有缓存，秒 | 隔离 shader 缓存，秒 | GPU/CPU 比值总范围 | GPU 选择 |
|---|---:|---:|---:|---:|
| 1＋3 | 1.494 | 1.987 | 0.255–0.577 | 10/10 |
| 2＋3 | 1.579 | 2.205 | 0.274–0.584 | 10/10 |
| 2＋5 | 2.057 | 2.538 | 0.303–0.527 | 10/10 |
| 3＋3 | 1.830 | 2.329 | 0.285–0.523 | 10/10 |
| **3＋7，当前生产协议** | **2.633** | **3.097** | **0.271–0.353** | **10/10** |

全部 50 次的每次预热、正式采样均通过 CPU/GPU 文本及设备内重复输出一致性检查；没有无效比值、超时或误选 CPU。
前四种候选协议中的 1＋3、2＋3、2＋5、3＋7 按轮次轮换顺序执行；观察到短预热在隔离缓存时波动较大后，追加 3＋3 的 10 次对照。

3＋7 的 worker 中位耗时为 2.419 秒／2.871 秒；整个 Python 选择进程为 2.851 秒／3.307 秒。
此前 30 次常用缓存测量的完整设备选择耗时为约 2.5–2.7 秒，与本次结果相符。

**可以减少到 3＋3，保留三次预热，完整选择约省 0.77–0.80 秒。**
但其比值最大达到 0.523，3＋7 最大仅 0.353，不能因为本机远离 0.8 阈值就认定短协议在阈值附近同样可靠。
三次中位数只能抵抗一次极端采样，七次中位数可抵抗三次。综合结果，当前生产默认仍保留 3＋7；3＋3 作为优先减少等待的候选。
正常文件配置中的 `auto` 决策成功后会持久化，因此这项开销通常只发生一次；本次通过环境变量强制每个新进程重新校准。
阈值保持 **0.8**。本轮没有增加自适应重采样或修改生产轮次，也没有重新验证 Windows DML 硬件性能。

## NHWC 关闭 prepacking 的完整文档测试

输入为 demo1＋demo2 合并后的 19 页，SHA256 为 `06d0e74125b5d2e1fc04e658bbe4af39422d70abfaa453a87353df4d3dad3432`。
使用 `basic`、强制 `ocr`、ONNX 栈、4/1 线程，关闭 LLM 标题分级和跨页表格合并。
每次新进程串行运行，计时不启用 Python observer；包含模型会话初始化、预处理、推理、后处理，排除导入、下载、派生图预生成和结果保存。
各模型已有 GPU/CPU 路由保持一致，包括 MFR 非 8 批次、表格分类、SLANet Plus 等 CPU 路线。

在隔离的完整源码副本中，仅对 WebGPU 会话加入 `session.disable_prepacking=1`；CPU 会话保留默认行为。
`preferredLayout=NHWC`、GraphCapture、缓存及其他 WebGPU 参数均沿用生产设置。本轮没有运行 NCHW。

| 设备及设置 | 第一次，秒 | 第二次，秒 | 平均，秒 | 结果 |
|---|---:|---:|---:|---|
| CPU，之前同配置基线 | 96.009 | 98.113 | 97.061 | 参考结果 |
| 3060 Ti，prepacking 开启 | 49.875 | 49.816 | 49.846 | 两次各 50 个文件与 CPU 逐字节一致 |
| 3060 Ti，prepacking 关闭 | 50.446 | 50.428 | 50.437 | 两次各 50 个文件与 CPU 逐字节一致 |
| UHD 770，prepacking 关闭 | 212.656 | 失败，进程约 197.3 秒退出 | — | 第一遍内容错误；第二遍 GPU HANG |

NVIDIA 测试顺序为开启→关闭→关闭→开启，平均差 **0.592 秒，耗时增加 1.187%，吞吐下降 1.173%**。
每组两次样本且桌面未锁频，这是一组小幅差值，不应解释为固定比例的性能损失。
本机 NVIDIA 使用 **nouveau / Mesa NVK / Vulkan**，不是 NVIDIA 专有驱动或 CUDA；结论仅针对当前 WebGPU 环境。

物理设备通过 Vulkan ICD 隔离，且每秒采样 `/proc/<pid>/fdinfo`：Intel 两次只打开 renderD128 / i915 / `0000:00:02.0`，
NVIDIA 四次只打开 card0、renderD129 / nouveau / `0000:01:00.0`。没有把 ORT 注册设备描述误认成 Dawn 的实际物理 GPU。

### UHD 770 第一遍：完成不等于正确

19 页及 50 个文件均成功保存，但有 30 个文件与 CPU 不同，包含裁切图、Markdown 和三个 JSON。
部分图片差异可由裁切坐标变化引起；判定失败的依据还包括明确的语义错误：

- CPU 中 `N_{zero}` 的行内公式在 Intel 结果中出现重复嵌套和缺失括号。
- 正文存在截断、段落边界和阅读顺序变化。
- 表格出现转向和明显乱码，不能作为正常识别结果。

CPU / Intel 顶层 block 数为 257 / 266，Markdown 为 80,574 / 80,005 字节。
两者均有 16 个块公式、101 个行内公式和 7 个表格；按同页出现顺序对照，分别有 11、60、4 个内容位置不同。
这些数字包含顺序变化，不是基于人工标注的模型错误率。逐页统计及具体样例保存在 JSON 报告，完整 Markdown 差异保存在原始证据目录。

### UHD 770 第二遍：NHWC 也发生挂起

同一设置的新进程完成 layout 和 151 项公式识别，进入 OCR-det 后在约 192/252 处失败。
Vulkan 提示 `VK_ERROR_DEVICE_LOST`，随后 ORT 在 `BufferManager::Download` 报 `Failed to wait for the operation:2`。
内核新增记录为：

```text
Oct 21 21:02:02 ... i915 0000:00:02.0: [drm] GPU HANG: ecode 12:1:85dcfffb, in python [27556]
```

进程总墙钟约 197.3 秒是失败退出时间，不能当作完成解析的耗时。
第一次成功遍历和第二次挂起共同说明：禁用 prepacking 不能保证此机器上 NHWC 的整本正确性与稳定性。
此前六图 rec 和两页 layout 的恢复只代表那些输入通过，不能扩展为所有模型、输入尺寸和执行序列均已修复。
本轮没有捕获失败批的完整原生 shader / GPU error-state，因此不能将 Download 报错本身或某一个模型算子定为根因。
检测到挂起后停止后续 Intel GPU 校准及独立张量回放；没有继续用其他布局重试。

## 0.8 阈值及代码状态

五种轮次的 50 次默认双卡自动选择均实际走 NVIDIA 路线，文本一致，按 0.8 全部选 GPU。
另有 5 次 NHWC＋禁用 prepacking 的 NVIDIA 3＋7 自动选择，全部选 GPU，比值 0.304504–0.342971。
本轮没有新的 Intel 禁用预打包自动选择数据，原因是完整测试已经触发挂起，随后停止 Intel GPU 试验。
这些结果支持 3060 Ti 的选卡结论，不足以推导新的跨硬件阈值或保证仅依赖六图 rec 就能覆盖整本稳定性。

生产代码仍采用 3 次预热、7 次正式采样中位数和 0.8 阈值；禁用 prepacking 与短轮次均只在隔离源码副本中测试。
真实用户配置 SHA256 保持 `5c447bf9c2834991aba50a86cd5a435a4753a0ad6a6e21b745e685670fd59e99`。
